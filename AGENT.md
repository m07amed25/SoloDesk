# SoloDesk — Agent skill selection and development guide

Updated 17 October 2026. This file documents the **34 project-local skills** and **18 additional session-provided skills** available when checked. It selects workflows; it does not execute them or authorize implementation. [AGENTS.md](AGENTS.md) is the short repository entry point pointing here.

## 1. Read before project work

Read the user's current request and relevant sections of [PRODUCT.md](PRODUCT.md), [decisions](docs/planning/decisions.md), [roadmap](docs/planning/roadmap.md), [requirements](docs/product/requirements.md) and the feature's specification. Use [coverage](docs/planning/coverage.md) to locate stable IDs; use the [documentation index](docs/README.md) for other concerns. Do not load every skill or every large specification indiscriminately.

**Current authorization includes F001 delivery-governance implementation. Business-feature work remains documentation only.** The previously authorized welcome shell exists; business features/cloud/encryption/portal are unimplemented. A later user request can authorize implementation for its stated scope without repeatedly asking for permission already granted. A skill, task list, phase checkbox or scaffold never expands that scope by itself.

Follow system/developer instructions, the user's authorized task, applicable repository guidance and the selected skill instructions. User scope/choices take precedence over conflicting skill guidelines. A skill is a workflow source, not permission to install packages, rewrite the app, publish, provision paid services or send external messages. Do reversible necessary work within authorized scope; ask concise questions only for material missing decisions/approval genuinely required.

## 2. Fixed product constraints

- Electron/React/TypeScript desktop on Windows, macOS and Linux; Electron Forge/Vite are the current tooling.
- Tailwind CSS and shadcn/ui are mandatory. Library suggestions cannot silently replace them.
- Freelancers and small teams from first usable release; managed-cloud accounts required, with offline support and current tenant/project/action authorization.
- Draft invoices offline; final issuance online under authoritative financial transactions. Exact money/time, immutable snapshots, idempotency and source-consumption protection are essential.
- Encryption in transit/at rest and encrypted device storage; installed better-sqlite3 is not an approved encryption implementation.
- English and Arabic with full RTL from first release; locale, permissions, offline states and recovery belong in every relevant feature.
- No AI product features for now. This excludes adding model-based app capabilities, not using an assistant or development/document tools.
- Prefer efficient low-cost/free services when suitable. Supabase-first backend is a documented recommendation with quotas/upgrade/recovery gates, not a provisioned service or free-production guarantee.

## 3. How to select and use a skill

1. Identify the task's outcome: explain/explore, specify/plan, audit, implement, debug, or deliver an artifact. Check scope and phase first.
2. If the user names a skill, read its actual SKILL.md and apply it within that scope. Otherwise select the narrowest relevant primary workflow; add a supporting specialist only where it improves the result.
3. Tell the user when first applying a skill. Read its complete instructions and necessary referenced resources before following it; catalogue summaries below are not replacements.
4. Verify prerequisites, installed framework, active feature/artifact paths and available tools. Missing files/CLI/credentials are real gaps, not permission to invent output or silently switch workflow systems.
5. Preserve project decisions and link generated artifacts to requirement IDs, phase and acceptance. Explain assumptions and update complex decisions rather than guessing financial/security behavior.
6. Verify the actual result using the appropriate checks. A review/plan is not implemented code; a successful build is not passed financial/security/RTL behavior. Do not create redundant implementation-mirroring tests for small reversible edits.
7. If instructions require a pause/approval, identify the exact skill path and relevant instruction and explain why it applies. Do not invent an extra approval gate merely because a skill is present.

Modes below: **R** read-only analysis; **D** creates/edits planning documentation; **C** may change app code; **X** may affect external services; **Asset/Artifact** generates files/media; **Setup** can change tools/dependencies. Even R/D workflows can run hooks or scripts: read the selected instructions before executing them.

## 6. Specification workflow prerequisites

**Observed state, 17 October 2026:** `.specify/` exists with templates/scripts and [constitution v1.0.0](.specify/memory/constitution.md). F001 implementation is authorized; product feature work remains deferred. There is no repo-local `openspec/` directory and no `openspec` executable on the inspected PATH. These observations must be rechecked when selecting the workflow; they are not permanent assertions about every machine or an external OpenSpec store.

For Spec Kit features: establish the constitution from confirmed project principles when requested/needed; do not treat commented template examples as approved policies. Then specify → clarify material gaps → plan → tasks → analyze/check requirements quality → implement only within the user's implementation request → converge remaining work → validate evidence. Check each skill's actual prerequisite rules and feature-path resolution scripts; do not hardcode a feature directory or invent a branch. Inspect applicable extension hooks before running the workflow and keep hook behavior within the user's authorized task; hooks do not override scope or external-action restrictions.

For OpenSpec: confirm CLI, authoritative store/root and selected change. Explore → propose planning artifacts → apply only for an implementation request → archive only completed verified work. Do not initialize/migrate a second planning system just to edit AGENT.md. If a user explicitly selects OpenSpec, explain concrete missing prerequisites and resolve them within authorized setup scope instead of silently substituting Spec Kit. Preserve the original skill's planning/implementation boundaries.

The `speckit-taskstoissues` skill is deprecated and has external side effects. Its source describes a replacement extension; do not install or enable that extension automatically. Creating GitHub issues or sending messages requires the relevant explicit authorization.

## 9. Maintenance and validation

When adding/removing/updating a skill, compare the live session catalogue with project-local `.agents/skills/*/SKILL.md`, update purpose/mode/prerequisites, and verify links. Read the source rather than assuming a name such as “upgrade” applies to every updater. Never rewrite installed skill files or install optional dependencies as part of catalogue maintenance unless requested.

If a skill or required supporting example/resource is missing, state the exact missing path; do not claim to have followed it. Use an appropriate documented fallback/official source where allowed, or stop only the dependent action and explain the concrete blocker. Current-version API/security/provider facts need primary-source verification at implementation time.

Before reporting a task complete, state what changed, how it was checked and any unresolved limitation. Keep source specifications/acceptance/current implementation status separate. For this guide, validation is skill inventory/path/link consistency; no app implementation or workflow execution is needed.

Delivery governance: [contributor and review policy](docs/development/delivery-governance.md).

F002 implementation is authorized by the current user request. Its [verification commands, native/security scope and recovery](docs/features/F002.md) and actual QA remain distinct from business-feature implementation, owner approval, merge, protection activation and release.
