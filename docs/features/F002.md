# F002 — Automated CI and Verification Harness

Status: implementation in progress. [Specification](../../specs/002-ci-verification-harness/spec.md), [technical plan](../../specs/002-ci-verification-harness/plan.md), [tasks](../../specs/002-ci-verification-harness/tasks.md), [QA](../qa/F002.md).

The verification CLI distinguishes scoped baseline success, complete automated readiness, actual agent QA and final owner approval. Only observed execution counts as evidence.

F001 actual merge is verified. Customer workflows, encryption, cloud, financial rules, Arabic UI and release signing remain outside F002.

## Baseline commands

Use `npm ci --ignore-scripts --no-audit --no-fund` for locked setup. `npm run verify -- --profile baseline --base <actual-full-base-sha>` runs type/lint/build, launcher, F001 governance, documentation and verification contracts. Its scoped exit 0 is not full readiness; security/native/agent/owner stages remain separately required.

`npm run test:unit` and `npm run test:integration` invoke fixed leaf runners. Required zero/partial/skipped/TODO suites fail; recorded command strings never execute. Logs and JSON are bounded and redacted.

Ordinary isolated Node execution is the authoritative runner. In this restrictive tool sandbox, nested TAP output is unavailable; tests were separately executed outside that sandbox and report actual assertion counts. This is a tooling limitation, not a waiver.

## Aggregate and provenance

`node tooling/verification/cli.mjs context --mode local --base <full-sha> --out .verification/review/context.json` captures actual local head/base and dirty-file hashes. `select --context .verification/review/context.json --out .verification/review/selection.json` declares the mandatory baseline/security and risk-selected native targets. `run --group baseline`, `run --group security` and `verify --profile desktop --target linux-x64` are scoped commands. `verify --profile all` fails while any selected target or scanner is missing/failed. Supply the actual comparison base for reproducibility.

`aggregate --context <owned-context.json> --selection <owned-selection.json> --reports <owned-report-directory>` compares required obligations, command/count/target bindings and reports. Hosted aggregation freshly inspects the actual run/attempt/jobs/current PR; editable provider JSON cannot supply authentication. `inspect --context <owned-context.json> --run-id <integer> --attempt <integer> --pr <integer>` is read-only and requires GitHub authentication. JSON is default; `--format text` preserves classifications and exit codes. Exit 0 means requested scope passed, 1 means a blocking finding, and 2 means invalid/unavailable infrastructure. No command approves or merges.

The first F002 proposal is explicitly bootstrap-candidate policy. Subsequent hosted metadata dispatch selects the evaluator and baseline minimum from the actual base before importing its modules; candidate additions cannot reduce existing check definitions. Candidate workflows/tests still require actual diff review: a check name and Actions app do not make a workflow immutable. Producer subprocesses receive an allowlisted environment without GitHub tokens. Metadata credentials are used only by the separate read-only gate.

## Real desktop and enrollment

Build with `npm run build`, install the locked runtime with `npm run setup:electron`, then run `npm run test:desktop`. The test-only bootstrap validates verifier-owned userData/sessionData directories and sets both before readiness, then requires the fixed unchanged built main. The actual smoke checks the welcome heading, ready state, expand/collapse/disclaimer, runtime sandbox/context isolation/disabled Node integration and absence of renderer require. It collects a synthetic PNG and closes/removes only owned profiles. Linux headless execution requires Xvfb and the locked Electron sandbox helper owned by root with mode 4755; the workflow configures that normal prerequisite only on its ephemeral Linux runner. a missing display/sandbox/runtime is blocking. Never disable sandboxing to repair automation.

Validation targets are Linux x64 on ubuntu-24.04, Windows x64 on windows-2025 and macOS arm64 on macos-15. Each has an independent report; one result cannot substitute for another. These targets do not decide product distribution/support Q-11, signing or release certification.

Future suite IDs are unique and namespaced by their owning feature, for example `F999:synthetic-demo`. Supply real entry files, stable feature-prefixed scenario IDs, independent positive/negative assertions and specialist categories; validate with `validateEnrollment` in `tooling/verification/enrollment.mjs`. Enroll the reviewed fixed Node argv and actual minimum assertion count in `verification/suites.v1.json`; all baseline/security entries are mandatory. Missing/empty entries fail. The explicit fixture `tests/verification/fixtures/enrollment-demo.mjs` demonstrates a real passing and failing synthetic enrollment and is excluded from ordinary discovery. It claims no business-feature implementation. Future English/Arabic/RTL/accessibility, finance, authorization, sync, storage, documents, provider and release obligations remain explicitly unimplemented and require their own real cases and applicable manual review.

## Security, bounds and recovery

`npm run check:security` runs pinned Gitleaks 8.30.1, all-dependency npm audit, the complete lockfile SPDX inventory and pinned actionlint 1.7.12 plus workflow policy checks. actionlint runs without optional external ShellCheck; shell privilege/pinning policy is checked explicitly and reviewed. Gitleaks scans a bounded contribution-only snapshot of tracked/nonignored files; ignored local environment/customer files are never copied or published, and symlinks are scanned as inert link text. Archive SHA-256 and tool version are verified before use. Tools may download only their reviewed official pinned archives; unavailable network/checksum/version blocks. Raw secret reports are removed and only safe finding metadata is shared. The exact documentary lifecycle phrase and known synthetic fixture sentinels have narrow path/value allowlists.

Every advisory severity requires responsible triage. Unknown/conflicting license metadata blocks; valid SPDX metadata is an inventory result, not legal approval. `verification/scanner-dispositions.v1.json` currently waives nothing. A disposition must bind exact finding/package/version/severity/scope with owner, rationale, evidence and expiry; credential exposure, privilege bypass and constitutional blockers cannot be waived by JSON. There is no audit-fix command.

Limits: local coordinator 45 minutes; hosted context/baseline/security/native/aggregate 5/15/10/20/2 minutes; hosted execution 50 minutes; launch/case 30/60 seconds; graceful/total cleanup 10/20 seconds. Desktop uses one worker and zero automatic retries; matrix parallelism is two, fail-fast false. Manual reruns retain attempts. Same-proposal concurrency cancels superseded runs, leaving other groups separate; actual cancellation timing needs provider evidence.

Inputs are at most 2 MiB each/32 MiB combined, 512 definitions/2,048 records. Safe UTF-8 JSON/text and synthetic PNG only; traversal, symlinks, active/encoded content, digest/identity mismatch and expired evidence block. Logs/screenshots are limited to 2/5 MiB, generic jobs 25 MiB and the run 100 MiB. Reserved allocations are baseline/security 10 MiB each, 20 MiB per native target and 10 MiB combined metadata. Uploads are prevalidated, retained seven days, with no videos/HAR/traces/core/build/dependency archives. Required artifact expiry/access loss blocks current evidence, even if the historic test result remains true.

Cross-run cache restore/save is disabled. Use fresh disposable checkouts and script-disabled `npm ci`; only the reviewed Electron setup step runs for native work. Never reuse node_modules/native/.vite/results/evidence across targets or trust contexts. On failure restore the named tool/network/display/evidence prerequisite, preserve the failed attempt and rerun affected checks. Cleanup targets owned processes/profiles only; unresolved cleanup/flakiness remains a defect. No paid capacity is provisioned.

## Adoption and current limitations

Read-only inspection on 18 October 2026 found a public repository, main default branch, admin access, Actions enabled, read-only default workflow token and first-time fork-contributor approval. No branch protection or rulesets existed. Protection is prepared and unactivated; no settings were changed. Once a real observed `F002 / automated-readiness` identity exists, the proposal is strict current checks/resolved conversations while preserving stronger existing controls. Final owner approval remains separate; independent review is required only where actually mandated/adopted. Activation and any recovery changes need separate explicit authorization and observed verification. Restore a broken reviewed check identity before proposing protection changes; never bypass an existing constraint.

The initial actual audit reports seven high findings in shadcn's braces dependency chain; the registry currently offers braces 3.0.3, within the advisory's vulnerable range. No dependency downgrade, suppression or legal acceptance was inferred. See [QA](../qa/F002.md) and [evidence](../qa/F002.evidence.json) for current blockers, actual native/hosted scope and attempts. App/customer data/API/financial/locale behavior and the confirmed/recommended/open decisions are unchanged. F002 is incomplete until current evidence, agent QA, explicit final owner approval and actual merge satisfy delivery governance; green checks alone do not authorize merge or release.
