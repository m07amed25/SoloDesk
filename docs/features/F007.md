# F007 — Encrypted local persistence and migrations

Status: **synthetic candidate implementation in review** (19 October 2026). [Specification](../../specs/007-encrypted-local-persistence/spec.md), [plan](../../specs/007-encrypted-local-persistence/plan.md), [tasks](../../specs/007-encrypted-local-persistence/tasks.md), and [observed QA](../qa/F007.md) serve distinct purposes. No customer data, cloud synchronization, enrollment, release, or production approval is implied.

## Delivered local boundary

- `PersistenceService` owns one active workspace database per trusted F004 profile. Storage is physically partitioned at `userData/workspaces/<profile_id>/<workspace_id>/store.db`. The extra profile segment enforces the specification's account partition alongside the F006 envelope identity binding.
- `ProtectionOwner` obtains a 32-byte key from its OS-backed provider. `DatabaseConnection` selects SQLCipher v4 explicitly, verifies an existing store before schema work, uses WAL, enforces foreign keys, keeps temporary tables in memory, and has no plaintext adapter fallback.
- Local `_entity_example` mutations and matching `outbox_operations` entries commit in one transaction. Expected revisions, parent scope, payload bounds, and workspace IDs are checked. F017 owns actual sync dispatch and reconciliation.
- Existing unreadable stores enter a closed recovery state. A missing key, bad header, future schema, or incomplete namespace never causes an empty replacement. New namespace creation is retriable if key creation fails before a database exists.
- Metadata schema, monotonic versioning, pre-flight free-space checks, encrypted safety snapshots, migration journal transitions, startup snapshot restoration, and reference-dataset reconciliation are implemented. The 50 MB buffer is interpreted conservatively as 50 MiB.
- A narrow, caller-bound preload facade sends only validated persistence status and retry requests. The shell displays English and Arabic recovery guidance with RTL, keyboard focus wrapping, and an explicit warning about unsynced local drafts.

## Activation boundary

The current desktop has no F012 enrollment or trusted active workspace grant. Production startup therefore creates no workspace store and exposes no arbitrary workspace through the renderer bridge. An owned F002 test profile can opt into `F007_SYNTHETIC_WORKSPACE` to exercise the UI with synthetic data. The renderer cannot supply a profile identity, key, SQL statement, or path.

F006 still blocks customer-data adoption until its Windows x64, macOS arm64, and positive Linux keyring host proof and Q-07/Q-11 security decisions are complete. F010/F012 enrollment, F017 sync, and F023 attachment lifecycle remain separate features. No app-level promise of secure erasure is made for native SQLCipher process memory.

## Verification and recovery

Run `npm run test:f007`, `npm run typecheck`, `npm run lint`, and `npm run build`. The 16 owned Node test files are also enrolled as `F007:integration` in the F002 baseline evidence manifest. The [QA ledger](../qa/F007.md) records observed results and the six [quickstart scenarios](../../specs/007-encrypted-local-persistence/quickstart.md). The synthetic Electron recovery UI test is `tests/verification/desktop/f007-recovery.spec.mjs` and is enrolled in `npm run test:desktop`.

On an inaccessible store, keep `store.db`, its key envelope, and `.migration/` intact. Resolve device-vault or disk-space conditions before using Retry. A local draft that has not synced may exist only on this device; an account password reset does not recover a missing local key. The migration runner restores a verified prior snapshot after an interrupted step and reports that event instead of silently resuming writes.
