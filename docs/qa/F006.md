## Security & privacy audit findings (T049)

1. **Raw-file inventory completeness**: Scanned database (`data.db`), index, WAL (`data.db-wal`), journal (`data.db-journal`), temp files, staged files (`*.stage`), and rotation metadata (`rotation.json`). Verified 0 plaintext fixture markers (`rawMarkers`) exist in any application-controlled on-disk file across all test executions.
2. **Key redaction & zeroization**:
   - In-memory key buffers are zeroed via `Buffer.fill(0)` on `owner.lock()`.
   - Serialized state files (`dataset.json`, `rotation.json`, `*.stage.meta`) contain opaque binding IDs, hashes, and generation labels only; raw keys are never written to disk or logs.
   - Closed error responses map all internal exceptions to safe reason codes (`vault_locked`, `key_missing`, `protection_denied`, `unprotected_backend`, `integrity_failed`, `interrupted_rotation`, `unsupported_format`) without exposing paths, queries, or stack traces.
3. **Threat model limitations**:
   - Compelled user unlock or same-OS-user process memory inspection during active session are acknowledged as platform limitations in `docs/architecture/security-and-privacy.md`.
   - Unprotected Linux backend (`basic_text`) is strictly rejected, preventing unencrypted fallback on misconfigured systems.

## User recovery & support guidance (T050)

- English and Arabic guidance in `packages/localization/src/shell/en.ts` and `ar.ts` rendered via `app/renderer/shell/App.tsx`.
