## PR #6 CI follow-up

The first hosted run for commit `792892c` ([run 39153211470](https://github.com/m07amed25/SoloDesk/actions/runs/39153211470)) passed context, baseline and security. All three desktop jobs failed, so automated readiness failed. The downloaded F002 desktop records show that each native wrapper reached its old 80-second limit. Windows and macOS first reached the F004 lifecycle test's 60-second timeout while waiting for a restarted view. Linux observed `isMinimized() === false` under the hosted virtual display, then timed out in the A/B restart case. These are failed observations, not target passes.

The repairs in `89ff4ec` raised the desktop wrapper budget to 150 seconds, preserved the 60-second per-case limit, recorded that the headless Linux display cannot establish native minimization, waited briefly for lock release before a same-profile restart and attempted to fail explicitly if the restarted process exited without a view. Invalid startup links now create the safe shell and deliver a buffered denial after its renderer subscribes. Notice text is selected at render time so switching language updates an existing denial. These repairs passed local F004 unit/integration, typecheck, lint, build, launcher and docs checks; the built Linux host suite passed 7/7 in `.verification/desktop-report-4435a36a-8ab8-4da9-bb72-49fd0d21b586`. A prior local rerun failed when the renderer build directory was absent during that run; a fresh build and an isolated link run passed before this full rerun. The local host result does not satisfy SC-001's 100 process trials or the Snap and fluent Arabic gates.

The next hosted run for `89ff4ec` ([run 39157657063](https://github.com/m07amed25/SoloDesk/actions/runs/39157657063)) again passed context, baseline and security but failed all three desktop jobs and readiness. Each desktop wrapper reached 150 seconds. Its lifecycle case reached 60 seconds after the first owner exited and the same-profile restart disconnected its inspector before a view appeared. The current process-exit race did not detect that early disconnect; the exact owner/startup state was not recorded. The next candidate adds verification-only lock/ready/failure markers for diagnosis on all three native runners.

A user-provided `npm start` screenshot showed a blank development window. An isolated Forge launch reproduced the cause: Forge wrote `.vite/build/preload.cjs` while the BrowserWindow requested `preload.js`. After aligning the Vite output and BrowserWindow path to `preload.cjs`, the same isolated development launch loaded the renderer, exposed the named bridge, and displayed the SoloDesk heading and controls. The original user's running process still needs a restart to pick up the change. The GPU VAAPI warning in the screenshot was incidental to this failure.

The hosted run for `750e9b7` ([run 39158683597](https://github.com/m07amed25/SoloDesk/actions/runs/39158683597)) passed context, baseline and security, but all three native desktop jobs and readiness failed. Verification-only markers show each restarted process acquired the single-instance lock and reached the ready state; it then raised `trusted-document-unavailable` while loading the renderer. This narrows the failure to trusted document loading after a same-profile restart, rather than a stale lock. A following candidate preserves the underlying `loadURL` error as the exception cause and exits promptly in the test environment on startup failure, so the next hosted run can identify the load cause instead of waiting for a modal dialog and the wrapper timeout.

The hosted run for `ce85034` ([run 39159306035](https://github.com/m07amed25/SoloDesk/actions/runs/39159306035)) marked all jobs green, but the downloaded Linux desktop report exposes a false-positive restart assertion: the second owner acquired its lock and created a BrowserWindow, then failed `loadURL` with `ERR_FAILED (-2)` for `solodesk-app://ui/index.html` and exited 1. The test asserted the window count before verifying a rendered document, so this green run is not valid restart evidence. The next candidate requires the heading to render after both same-profile restarts and records asset handler requests and responses to locate the protocol failure. Until that run is inspected, automated readiness remains unproven despite the CI status.

Final local scoped gates for this repair: `npm run verify -- --profile baseline --base 70c01757572bd3b08b4499d9d48db5619b78bf2f` passed every selected baseline suite (run `run-accc872d-c0c0-433d-861a-5db416637906`, including F004 unit 18 and integration 11 tests). `npm run check:security` passed secrets, dependencies, licenses and workflow syntax (run `run-d3c8654a-926a-4573-abc3-6c35441efcd3`).
