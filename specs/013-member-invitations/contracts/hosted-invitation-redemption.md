# Contract: Hosted Invitation Redemption

**Consumers**: Delivered invitation link, planned F010 `web/auth/` surface, F010 session authority, restricted invitation-redemption service/database functions.
**Boundary**: This flow is hosted in the browser. The invitation secret never enters Electron, preload, renderer, local workspace storage, or desktop deep-link routing.

## Link and Fragment Contract

The trusted delivery adapter constructs:

```text
https://AUTH_ORIGIN/invitation#SELECTOR.SECRET
```

- `selector` is a bounded random lookup identifier.
- `secret` contains at least 256 bits generated by a cryptographic random source.
- Neither value conveys workspace, recipient, role, scope, expiry, or provider identity.
- The full URL is assembled only in trusted delivery memory and must not enter persisted logs, receipts, analytics, crash artifacts, support bundles, or desktop messages.

On initial load the hosted client:

1. validates only the fragment's bounded syntax;
2. sends it once to the same approved origin over HTTPS using a body with `no-store` behavior;
3. replaces browser history immediately to remove the fragment;
4. never writes the value to console, telemetry, DOM attributes, local/session storage, clipboard, service-worker cache, or error text.

The hosted CSP, referrer policy, dependency allowlist, analytics, and service-worker behavior must be reviewed so third-party scripts cannot observe the exchange.

## `POST /invitation/exchange`

Conceptual request:

```json
{ "selector": "bounded", "secret": "bounded" }
```

The server performs bounded selector lookup, constant-time digest comparison, and current-generation/expiry/revocation checks. A valid exchange creates a short-lived redemption attempt and sets a random continuation cookie:

```text
Secure; HttpOnly; SameSite=APPROVED_POLICY; Path=/invitation; Max-Age=SHORT_APPROVED_WINDOW
```

The raw continuation is stored only in the cookie; only its digest is stored server-side. The response contains no invitation details.

Public responses are deliberately coarse:

```ts
type ExchangeResult =
  | { state: "continue"; next: "sign_in" | "review" }
  | {
      state: "unavailable";
      action: "request_new_invitation" | "try_again_later";
    };
```

Malformed, unknown, expired, superseded, revoked, consumed, and rate-limited tokens do not reveal which condition or whether any workspace/account exists.

## Sign-In Handoff

- If no current verified F010 session exists, the hosted page starts the approved sign-in flow while retaining only the HttpOnly continuation.
- The invitation is not an Auth credential and cannot relax MFA, recovery, callback, session, or issuer checks.
- Any return URL is fixed or strict-allowlisted to the same invitation route; caller-supplied origins are rejected.
- Sign-out/account-switch clears the current application session as F010 defines but preserves or rotates the redemption attempt only under the approved short window.
- Expired continuation requires reopening a current invitation link; it never falls back to cached review data.

## `GET /invitation/review`

Requires both a valid continuation and a live verified F010 session. The server resolves the session to stable `(issuer, subject)`, validates recipient binding, current generation, invitation state/expiry, workspace availability, and current offer policy.

For the matching intended identity:

```ts
type InvitationReview = {
  state: "review";
  invitationRef: string;
  workspaceLabel: string;
  inviterLabel?: string;
  roleLabelKey: string;
  scopeLabelKey: string;
  consequenceLabelKey: string;
  expiresAt: string;
  revision: number;
};
```

Labels are bounded, presentation-only, localized by closed keys, and rendered with bidi isolation. `invitationRef` is a safe display/correlation reference, not the database ID or a bearer value.

For a wrong account, missing authority, or unavailable invitation:

```ts
type InvitationReviewUnavailable = {
  state: "unavailable";
  action:
    | "switch_account"
    | "request_new_invitation"
    | "contact_inviter"
    | "try_again_later";
};
```

The response does not include workspace, inviter, recipient, role, scope, membership, or terminal-state detail. More specific expired/consumed/revoked guidance is allowed only after matching verified recipient identity and only if it does not reveal hidden tenant data.

Review responses use private/no-store cache policy and must not be indexable.

## `POST /invitation/accept`

```ts
type AcceptInvitationInput = {
  operationId: string;
  invitationRef: string;
  expectedRevision: number;
  confirmed: true;
};

type AcceptInvitationResult =
  | {
      ok: true;
      effect: "accepted" | "replayed";
      membershipRef: string;
      workspaceLabel: string;
      roleLabelKey: string;
      scopeLabelKey: string;
    }
  | {
      ok: false;
      code:
        | "invitation_unavailable"
        | "online_required"
        | "outcome_unknown"
        | "temporarily_unavailable";
      action:
        | "switch_account"
        | "request_new_invitation"
        | "retry_original"
        | "try_again_later";
      correlationId?: string;
    };
```

The server ignores any actor/workspace/role/scope/expiry supplied outside this schema and:

1. derives current stable identity from the live verified session;
2. claims or replays the F009 operation by semantic digest;
3. locks invitation, current generation, and membership key in that order;
4. validates continuation/generation, recipient identity, database expiry, workspace state, current policy/offer, and absence or exact identity of an existing membership;
5. inserts or returns exactly one active membership with accepted provenance;
6. consumes generation, invitation, and redemption attempt and writes the same-transaction receipt/evidence;
7. clears the continuation cookie after a known terminal result.

The success result is safe confirmation, not a desktop workspace-switch command. F012 discovers the new workspace through its own authoritative refresh/switch flow.

## Replay, Concurrency, and Unknown Outcomes

- Two sessions accepting the same generation serialize to one membership and one consumed invitation.
- A retry with the same operation ID/digest returns the recorded result.
- A different operation after commitment may receive the same safe accepted outcome only for the same verified recipient; it cannot create another membership.
- A response lost after commit returns `outcome_unknown`; the same operation is reconciled/retried before generating a new intent.
- Resend/revoke/expiry winning the lock race produces no membership. Acceptance winning produces one membership that later invitation history cannot remove.

## Abuse and Enumeration Controls

- Bound fragment/request sizes before database work.
- Rate-limit exchange and acceptance by approved combinations of origin, coarse network signal, selector, session, account, and workspace without returning account-existence differences.
- Equalize public status/body shape and avoid material timing distinctions where practical.
- Use allowlisted correlation identifiers; do not echo selector, secret, recipient, provider, or database identifiers.
- Do not expose list, search, count, workspace lookup, invitation lookup, or account discovery endpoints on this surface.
- CSRF protection follows the approved same-site/session architecture; state-changing requests require same-origin checks and the continuation/session binding.

## Hosted UI and Accessibility Obligations

- English and Arabic present identical workspace/access/expiry/consequence meaning.
- Email-like identifiers, safe references, and mixed Arabic/Latin labels use bidi isolation and preserve copy order.
- Sign-in, switch-account, confirm, retry, and stop paths work by keyboard with visible focus.
- Focus moves to the review heading or safe error summary after state changes; restrained live regions announce outcomes without hidden details.
- Review requires explicit confirmation; loading, expiry, wrong-account, consumed, revoked, unknown, and success states are not conveyed by color alone.
- Layout reflows at 200% zoom and respects reduced motion.

## Verification Obligations

- Browser tests prove the fragment disappears before navigation/analytics and never enters storage, logs, referrers, errors, or rendered markup.
- Wrong-account and signed-out tests receive zero protected details.
- Auth session/MFA/recovery tests show the token cannot bypass F010/F011.
- Database races and failpoints prove one membership plus consumption or no effect.
- Expiry uses database time under hostile device-clock tests.
- CSP/referrer/cache/cookie/CSRF tests validate the deployed hosted configuration, not only component behavior.
- English/Arabic, RTL, mixed-direction, keyboard, screen-reader, contrast, reduced-motion, and 200% zoom evidence is captured separately from desktop evidence.
